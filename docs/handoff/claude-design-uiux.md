### 현장 환경 (디자인 제약)
- 노트북 **1440×900**, 밝은 실내 조명 → **대비 충분히**, 다크모드 불필요
- 본문 16px 이상, 버튼 높이 44px 이상. 직원이 어르신과 **눈을 맞추며** 곁눈질로 누르는 상황 → 큰 타깃, 한눈에 읽히는 상태
- 와이파이가 끊길 수 있음 → 오프라인에서도 입력·완료 가능(이미 구현), **상태 표시가 늘 보여야 함**
- 로그인 없음. 첫 화면에서 담당자가 **자기 이름을 눌러** 시작(노트북에 기억)
- 키보드만으로도 진행 가능해야 함 (검색 Enter, 설문 Ctrl+Enter 완료)

## 2. 대상 구분 (화면에 A/B/C를 보이지 않음)

명단의 활동 기록으로 **자동 판정**되고, 직원은 고르지 않습니다. 화면에는 말로만 보입니다.

| 내부 | 화면 라벨 | 한 줄 설명 | 설문 목적 |
|---|---|---|---|
| A | 활동 중 | 최근 한 달 안에 사용하신 분 | 만족·불편·바라는 점 → 4기 유지 |
| B | 쉬는 중 | 예전에 꾸준히 하셨는데 한 달 넘게 쉬고 계신 분 | 중단 이유, 기억나는 게임(게임 카드), 복귀 조건 |
| C | 거의 미사용 | 앱을 거의 사용하지 못하신 분 | 못 쓴 이유 + **현장 설치·로그인·첫 게임** 체크 |

판정 기준(2026-09-14 추출본, 3기 891명): 최근 30일 안에 사용 → 활동 중 **301명(33.8%)** / 30일 넘게 안 썼지만 누적 20회 초과 → 쉬는 중 **158명(17.7%)** / 기록 없음 또는 20회 이하 → 거의 미사용 **432명(48.5%)**.

## 4. 문항 (현재 v3)

- 동의: 개인정보 동의*(동의/미동의) · 오늘 어떻게 알고 오셨어요(여러 개)
- 활동 중: 사용 빈도* · 좋은 점*(여러 개) · 즐겨 하는 게임(여러 개, 게임 17종) · 불편한 점*(여러 개) · 4기에 더 있었으면(여러 개) · 달라진 점(여러 개) · 추천 의향*
- 쉬는 중: 안 하게 된 이유*(여러 개) · 기억나는 게임(여러 개, 카드) · 좋았던 점(여러 개) · 다시 하려면 필요한 도움*(여러 개) · 다시 시작 의향*
- 거의 미사용: 못 쓴 이유*(여러 개) · 휴대폰 종류* · 도와주는 분(여러 개) · 현장 조치 체크리스트(설치/로그인/첫 게임 실행) · 막힌 지점*(여러 개) · 앞으로 사용 의향*
- 마무리: 4기 사전신청* · 안내받고 싶은 방법(여러 개) · 리워드 처리* · 실명(리워드 시, 선택) · 응대 결과*(설문 완료/일부 응답/응대 거부/재방문 예정) · 메모

대상별 필수 문항 수: 동의 1 + 대상별 4~5 + 마무리 3 = 약 8개. 문항 문구는 관리자가 바꿀 수 있으니, 디자인은 **문항 수·보기 수가 달라져도** 버텨야 합니다(보기 2~17개).

## 5. 이미 결정된 것 (바꾸지 말 것)

- 로그인 없음, 이름 골라 시작
- 설문은 **한 화면**(페이지 나누지 않음), 의견 문항은 **여러 개 선택 + 기타**
- 화면에 A/B/C·"트랙" 표기 금지 → 대상 라벨·설명만
- 본인 확인은 어르신이 **말한 뒷자리를 입력해 대조**
- 대시보드·응답 목록은 담당자 전원이 봄
- 명단은 3기만, 2기·1기 분은 "명단 외 추가 → 이전 기수"
- 목록 화면은 마스킹 이름, **본인 확인(상세)에 들어가면 실명**
- 글꼴 Pretendard, 토스 스타일 톤 유지
- 전체 휴대폰 번호는 앱 어디에도 표시하지 않음

## 6. 알려진 UX 문제 · 개선 기회 (검토 요청)

1. **찾기 결과에 뒷 4자리가 크게 보임 ↔ 본인 확인 대조의 의미가 약해짐.** 이름으로 찾으면 직원이 목록에서 번호를 이미 봄. 동명이인 구분을 위해 뒷자리가 필요했던 요구(원 지시서)와 충돌. 대안: 이름 검색 결과에서는 생년·연령·성별로 구분하고 뒷자리는 가리기? 혹은 뒷 2자리만?
2. **설문 화면 길이.** 대상별로 필수 8개 + 선택 6~7개, 게임 17종 보기 때문에 스크롤이 김(`12-survey-full.png`). 게임 보기를 카드 그리드/접기, 선택 문항을 "더 여쭤볼 것" 접기 등 밀도 개선 필요
3. **어르신 앞에서 읽는 문구.** 문항 제목이 직원용 문장과 어르신께 여쭙는 말투가 섞여 있음. "여쭤 볼 말"과 "직원 메모용 라벨"을 시각적으로 분리할지
4. **완료 흐름의 리듬.** 응대 완료 → 완료 화면 → 다음 분 찾기 → 검색창. 줄 서 있는 상황에서 1초라도 줄일 방법(완료 토스트 후 바로 검색으로?)
5. **상단바 정보 밀도.** 동기화 상태·완료 수·입력자가 한 줄. 오프라인일 때 더 눈에 띄어야 함(현재 빨간 배지)
6. **대시보드 가독성.** 문항 카드가 많아 긴 페이지. 요약(상위 3개 답변) → 펼쳐 보기 구조, 대상 비교 보기(같은 문항을 대상별로 나란히) 검토
7. **응답 목록 → 수정** 진입 시 "완료된 응답 수정 중" 배지만 있음. 실수 수정인지 이어서 입력인지 구분, 수정 이력 표시 여부
8. **본인 확인 모달(다른 직원이 응대 중)** 문구·버튼 위계
9. **명단 외 추가** 폼의 "명단에 없는 이유" 선택지와 대상 매핑 질문 문구
10. 색: 대상 배지(파랑/주황/보라)와 상태 배지(초록/주황/빨강)에서 주황이 겹침. 상태색과 대상색 체계화
11. **4기 신청자 화면**: 행사 중 실시간으로 늘어나는 숫자를 더 눈에 띄게(상단바 배지?), 번호 비표시 안내의 위계

## 7. 기대 산출물


- 화면별 개선 시안 (1440×900 기준), 특히 **찾기 · 본인 확인 · 설문 한 화면 · 완료 · 대시보드**
- 컴포넌트 규격: 선택 버튼(하나/여러 개/기타), 상태 배지, 동기화 표시, 진행바, KPI 타일, 분포 막대

- 가능하면 Tailwind 클래스 수준이나 HTML 목업으로. 구현 쪽에서 그대로 옮깁니다

## 8. 구현 쪽 참고 (디자인이 깨지 말아야 할 계약)

- 접근성 이름: 검색창 `aria-label="검색"`, 뒷자리 입력 `aria-label="어르신이 말한 뒷 4자리"`, 버튼 이름 "본인 확인 완료 / 다른 분입니다 / 확인 못 했지만 진행 / 응대 완료 / 다음 분 찾기" — 테스트가 이 이름으로 동작합니다. 바꾸면 알려 주세요
- 선택 버튼은 `role=radio|checkbox` + `aria-checked`
- 데이터: 응답 `answers[key]`(여러 개 = 배열), 기타 입력 `answers[key__etc]`
- 오프라인 우선 저장, 동기화 대기 건수는 숫자로 항상 표시(요구사항)
